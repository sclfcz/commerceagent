# 评测升级第一步：分层归因与对抗性审查

日期：2026-11-01。范围：离线失败归因、独立复评适配、人工证据标签、匿名诊断汇总。审查方式为本轮实现者的对抗性自审、故障注入测试和既有原始证据复放，**不宣称经过外部独立审查**。

## 原则与边界

- 检查失败是观察结果，不自动证明某个根因。参考答案通过、fixture 可重放，只能验证已有契约，不能以排除法认定模型有错。
- 机器默认输出未确定，同时保留所有风险信号。人工根因标签需要复核者、理由、证据版本、文件 hash 和字段引用。
- 首个失败层是展示顺序，不是因果顺序。其余检查、安全检查、不适用与不可评估状态继续保留。
- 归因与任务评分分开。此次没有修改用例、期望答案、工具调用上限、重试次数、质量分母或排名。
- 新归因入口只接受 dev；不读取 holdout 用例或参考答案，不更新留出集运行 ledger。既有全量单元测试仍包含离线 Schema/oracle 自检，不进行留出集模型运行。

## 审查发现与处理

| 攻击或反例                                                | 旧问题或本轮发现                                           | 修正与验证                                                                     |
| --------------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 所有评测自检通过，但业务标准仍可能不正确                  | 排除法默认 `model_error`                                   | 默认 `unresolved`；只有有证据的人工复核能确认原因                              |
| 传输失败、缺失 trace、fixture 损坏同时出现                | 测量错误可能被混入 fixture 类别，或只保留首个原因          | 分别保留测量、数据、断言风险；缺失证据不升级为 Agent 原因                      |
| summary 删除一条失败尝试或伪造通过                        | 仅遍历 summary 会漏样本                                    | 与独立原始证据核对尝试全集；缺项纳入复核，错配与重复 ID 拒绝                   |
| 原始 result 与 summary 使用不同字段名                     | 历史 result 的 `business` 不能按 `businessChecks` 直接读取 | 显式适配；两种字段同时存在且矛盾时拒绝核验                                     |
| 归档契约与当前契约不同                                    | 两套预期可能被混成一个失败数                               | 分别保存当前诊断和归档契约诊断，漂移保留为待核验                               |
| 检查从 true 改为 null，但整个任务判定不变                 | 检查项变化可能被误读为任务变化                             | 分开统计任务判定、测量判定和检查状态变化                                       |
| JSON 无法解析或某检查不适用                               | null 可能被 `!pass` 错算为失败                             | failed、not_evaluable、not_applicable 明确分开                                 |
| 格式先失败，同时发生注入或工具问题                        | 短路可能掩盖次要问题                                       | 不短路检查，保留安全结果；首层字段不作为根因                                   |
| 复制其他尝试的 result、标签或证据引用                     | 类别正确但证据属于别的执行                                 | 绑定 candidate、case、执行序号、重复轮次、原始输出及契约 hash；跨尝试引用拒绝  |
| 复用旧标签、修改证据、复评中途改文件                      | 旧判断可能套在新数据上                                     | evidenceRevision、字节 hash、JSON Pointer 和复评前后来源核对；不一致拒绝写报告 |
| 路径逃逸、符号链接、holdout 引用                          | 人工证据入口可能越过目录边界                               | 逐层校验相对路径与符号链接；拒绝相关输入                                       |
| 用空白模板、任意字符串或普通 trace 确认 Judge/Rubric 问题 | 未复核标签或无关证据可能被接受                             | 空白项不计确认；类别枚举校验；Judge 输入须绑定尝试，Rubric 须引用同一用例      |
| 旧重判入口再次生成“模型错误”标签                          | 新报告可能被旁路的旧分类抵消                               | 重判 schema v3 只报告判定转移，根因保持未确定                                  |
| 重跑工具覆盖旧报告、向公开汇总夹带内容                    | 证据丢失或隐私泄漏                                         | 版本化且不可覆盖的 sidecar；公开汇总仅含固定分类和计数，并复用身份泄漏检查     |

这些测试验证工具按契约拒绝不可信结论，不能证明人工业务标准或人工根因判断一定正确。

人工可以显式记录“已复核但仍未确定”，并保存理由与证据；这种记录不算确认根因，不会使完成门槛通过。未填写的模板也不会被当作人工结论。

- 既有 50 条 dev 原始记录离线复评：独立测量有效 50/50，当前契约通过 43/50；相对原 summary 有 3 条任务判定变化，47 条检查状态差异，当前业务失败 7 条。归因报告将这些版本差异保留为待核验，没有自动确认任何 Agent 根因。
- 新私有诊断文件为 `failure-review.05116eb4fe7e.json`；重判文件为 `business.regraded.5f8368845b65.json`。它们是旧数据的派生诊断，不是新的模型运行，也不替代原结果。
- 对复评前的 1,250 个原始文件逐一比较 SHA-256，没有文件被改写或删除；新增产物只写入私有结果目录。候选与 Judge 的真实模型调用数为 0。

## 保留限制与后续顺序

- 人工确认是带证据、可追溯的判断，不是程序给出的因果证明；`agent_error` 还可能来自 Profile 或工具策略，不能直接等同于某个模型能力不足。
- 旧规则发生漂移时，保留未确定是预期行为。没有人工确认的历史标签不能自动迁移成已确认结论，不能为了让门槛变绿而覆盖旧结果。
- 当前入口处理确定性失败和测量/记录分歧，尚未自动导入 Judge 失败作为新的复核样本。Judge 校准和模型排名资格没有因此提升。
- 离线重判仍沿用原运行的测量与身份资格，只能作为诊断；它不是一次新的独立资格重认证，不能用其中的展示指标替代正式选型所需的原始证据复评与预登记规则。
- 下一步是逐轮证据归属及能力覆盖；再下一步是独立 Judge 验证集。在线抽样与业务效果验证放在后面，仍需数据与人工校准条件。
